# Prototype Instructions

Run the local server yourself and open the preview in the browser available to this environment. Do not give the user server-start instructions when you can run it.

Before making substantial visual changes, use the Product Design plugin's `get-context` skill when the visual source is unclear or no longer matches the current goal. When the user gives durable prototype-specific design feedback, preferences, or decisions, record them in `AGENTS.md`.

When implementing from a selected generated mock, treat that image as the source of truth for layout, component anatomy, density, spacing, color, typography, visible content, and hierarchy.

Build app UI in `src/`. Keep `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, and `tests/sites-worker.test.mjs` intact so the same local prototype can be handed to Sites. Before a Sites handoff, run `npm run build` and `npm run test:sites`; the build must leave `dist/client/index.html`, `dist/server/index.js`, and `dist/.openai/hosting.json`.

## Durable RF Monitor Decisions

- Keep the default dashboard operator-first: plain-language status, affected service/frequency, observation, recommended action, evidence state, and evidence-package download. Spectrum, waterfall, metrics, history, and display controls belong behind Engineer details.
- Render service labels, frequency definitions, profile selections, site identity, time zone, thresholds, and retention from backend catalog/profile data. Do not duplicate deployment values in React constants.
- RF Monitor 1.0 has no LAN access token. Network admission is handled by HTTPS/Nginx/firewall; only Settings writes require the short-lived protected session.
- Ubuntu production and test services use system `/usr/bin/node`, never a private NVM runtime.
- Installation and troubleshooting documentation must assume the reader is unfamiliar with Linux, Node.js, Nginx, and WebSockets. Give copyable commands, expected results, stop conditions, and safe recovery steps without embedding credentials.
- RF evidence may support an interference finding but cannot prove deliberate jamming intent. GNSS spoofing remains suspicion-only without independent navigation-receiver data.
- Graphs and incident history must be understandable to operators without RF or electronics training: label relative values explicitly, explain visual encodings in plain language, and lead incident records with impact, observation, recommended action, and evidence strength before technical details.
- Spectrum and waterfall must share identical frequency bounds and aligned guides. Explain expected reception versus possible interference in plain language, and never present RF plots as proof of deliberate jamming.
- The approved desktop baseline is a fixed-height 1920×1080 / 1366×768 control-room workspace: compact top controls, aligned spectrum over waterfall, and an operator status/incident rail. Spectrum and waterfall remain visible without page scrolling; incident and engineer details open in an overlay drawer.
- Live browser streaming is adaptive: 2 Hz for the normal operator view, 4 Hz only for visible Engineer mode, and 0.2 Hz for hidden tabs. Coalesce obsolete frames and cap per-client backpressure rather than allowing queues to grow.
- Receiver health must distinguish SDRplay USB presence, SDRconnect transport, and live RF-frame flow. A physically present but stalled receiver gets bounded automatic SDRconnect recovery plus a clear operator Retry action.
- The selected dashboard direction is the Quiet Mission Board: a concise navy command bar, spacious default 2x1 feed wall, pinned shelf, and one-line status/evidence footer. Use blue received activity, a green learned baseline, red anomaly segments, and aligned waterfall trails. Keep engineer controls and incident detail in the overlay drawer.
- Pins are backend-derived monitoring feeds. GNSS signals that share one physical capture window are combined, such as GPS L1 / Galileo E1 / BeiDou B1C. StarTrack and 4DX are timestamped stitched surveys. One RSPdx can mark only one physical window Live; all other feeds must show paused, scanning, stale, or unavailable truthfully.
- Use short control-room copy throughout the application. Prefer Normal, Checking, Alert, Recovering, Live, Scanning, Data late, Paused, and Offline. Show operator evidence as Low, Medium, or High; keep percentages in engineer-only data. Use the disclaimer: RF data can show interference, not intent.
- Default to 2x1 and retain 1x1, 2x2, and 3x3 choices plus up to nine ordered pins. The 3x3 view is spectrum-only and expands a selected feed to 1x1. Use concise, direct control-room copy and do not add explanatory AI-style prose to the normal dashboard.
- Keep footer destinations distinct: Incidents opens the selected/current incident detail, Evidence History opens a persisted session-and-event archive with description, lifecycle status, timestamps, and per-session/per-incident downloads, and Engineer opens only engineering tools. Evidence History must not require Engineer mode.
- Keep the normal dashboard footer limited to Monitoring, Recording, Incidents, and Evidence History. Do not render Data or Production qualification in the footer; those facts remain available in Settings and System health.
- Keep 24/7 runtime work bounded: coalesce SDRconnect FFT input to 4 Hz per receiver, retain at most 2048 peak-preserving bins while analyzing the native input, record clear-state evidence every two seconds and alert-state evidence at processing rate, append raw evidence to hourly chunks, cap pending frame writes, and use cooldown/lockout recovery instead of restart loops.
- Keep field and test data as separate trust domains across runtime state, baselines, evidence, incidents, exports, commissioning, and deletion. A simulation or replay must never mutate field data, and the UI must keep Simulation/Test visible.
- Present current monitoring health and production qualification as separate states. A healthy receiver, a passing simulation, or a prior soak must never make an unqualified installation appear production-ready.
- The server owns the operator verdict, affected targets, timestamps, recording state, and qualification state. If live browser data or the client build becomes stale, fail closed with a direct Data late or Reload action while retaining any open incident.
- Signal learning is transparent robust statistics, not machine learning. Keep Clear test data, Restart signal learning, Delete recordings, and Restart software as separate protected actions with concise scope and retention copy.
- Evidence History uses the authoritative Active, Finalizing, Complete, Incomplete, and Corrupt lifecycle. Complete and explicitly gap-labelled Incomplete sessions may be downloaded; Active, Finalizing, and Corrupt full-session downloads stay disabled, and a legacy closed alias never implies Complete.
- Treat simulation as a separate test-data domain. Ambient simulation and synthetic exercises must never update, approve, clear, or appear as operational field baselines, evidence, incidents, or commissioning results; resetting test data must remain separate from resetting field learning or deleting field recordings.
- Simulation tests must be able to play through the existing main spectrum, waterfall, target state, alert, recovery, and incident UI. Keep playback server-authoritative, visibly marked Simulation/Test, time-gapped by the real one-tuner schedule, and completely separate from operational evidence, field baselines, and commissioning. Retain the isolated detector qualification report as a separate engineering check.
- Catalog/profile schema v3 uses explicit physical capture targets. Every logical signal has one `captureTargetId`; different tune centers may never be merged. The fast profile enables only the four Tier-1 targets by default and treats 2/6-second revisits as measured objectives, not guarantees.
- Production remains 10 MS/s with a configurable central analysis mask no wider than 8 MHz. Nine MS/s is experimental; request the configured SDRconnect sample rate only when needed and accept frames only after exact read-back confirmation. FFT bins remain uncalibrated uint8 relative values, and IQ is rejected and dropped.
- Baselines are exact-fingerprint, bounded reservoirs. Protected baselines are immutable, approval requires the protected Settings session, and RF-only v1 can emit Low or Medium evidence but never High.
- Enforce the live and evidence resource ceilings as hard bounds: eight dashboards, latest-only/coalesced frames, 256 KiB per-client queue, 64-item/2 MiB priority writer queue, 128 MiB raw chunks, 2 GiB/24-hour sessions, and numbered incident-export parts no larger than 256 MiB.
- Settings navigation is task-based and ordered Monitoring, System health, Recording, Site, Advanced. System health remains available without unlocking; editable pages use an explicit view-only state with a clear Unlock to edit action.
- Settings copy uses short labels and structured facts. Feasibility is evaluated from the unsaved draft, services report Monitoring, Paused, Will monitor, or Off, and paragraph-style hardware disclaimers do not appear in the normal settings flow.
- GNSS signal selection belongs in Monitoring. Advanced controls remain collapsed by task, baseline restart requires confirmation, and exclusive single-frequency focus belongs in the Engineer drawer rather than Settings.
- Unsaved Settings drafts are protected on close and on revision conflict. A conflict must preserve the draft and offer comparison, keep-draft, and load-server choices.
- Refine the selected Quiet Mission Board in place. Do not replace its navigation, dashboard layout, visual language, or interaction model when focused UX improvements can solve the problem.
- Normal-user health shows one overall state, one copy of each actionable issue, and a short set of plain-language checks. Trends, raw counters, queue metrics, network internals, timing distributions, and support commands stay behind a collapsed Engineer details disclosure.
- Present baseline work to normal users as Signal learning, grouped by active service with friendly readiness states and representative hours. Hide fingerprints, generations, observation counts, raw target IDs, inactive history, and reset controls behind engineer disclosures.
- StarTrack and 4DX are completed stitched surveys, not simultaneous live spectra. Their normal feed cards must receive bounded binary survey graphics and label them Last full sweep or Building first sweep; never show an unexplained blank graph or stretch a single physical window across the full service range.
- Present monitoring as four concise tasks within the existing Settings flow: Continuous Watch selects one catalog-defined GNSS or Fugro physical frequency window, GNSS selects two or more catalog-defined tier-1 GNSS windows, GNSS + Fugro selects those tier-1 GNSS windows plus every tier-1 Fugro capture target, and Radio Survey runs StarTrack/4DX with those windows off. Keep these tasks mutually truthful for the single tuner and do not add explanatory product-positioning copy to the normal UI.
- A task may relax a window's revisit objective through `scan.revisitObjectiveOverridesMs` so several windows fit one receiver; GNSS + Fugro keeps L1 at its 2 s objective because jammers target it, and relaxes the others. Objectives are never relaxed by editing the catalog, because `catalogVersion` is part of the baseline fingerprint and editing it would discard learned baselines.
- Keep scientific scope limits in validation records, evidence metadata, Engineer details, and documentation. Do not repeat long product-positioning disclaimers in normal internal-software screens; use short status, observation, coverage, and action labels instead.
- Synthetic validation results lead with the operational verdict and affected capture target: Suspected RF interference, Receiver overloaded, Test inconclusive, No RF anomaly, or a fail-closed validation error. Test pass/fail is secondary; matched-power controls remain neutral, and missed events or false alerts never appear green.
- A production candidate is fail-closed: the UI must distinguish current health from development qualification, provide operator-safe diagnosis and recovery without developer contact, and remain explicitly unqualified until hardware recovery, Tier-1 coverage, evidence continuity, protected baselines, and the bounded development gates through V7 pass.
- Development goals, release gates, acceptance tests, and agent-run tasks may not exceed 24 elapsed hours. V7 is the final required gate and the development plan ends there. Do not schedule V8/V9, expose them as development commands, include them in readiness, or wait for them as part of this project goal.
- Production qualification uses live field-domain data from the installed RSPdx/RSPdx R2 and final RF chain. V5 may replay only independently captured real receiver FFT data; V6 and V7 require the live physical receiver. Simulation, generated scenarios, IQ fixtures, and test-domain data remain regression/training evidence only and can never approve baselines, commissioning, or production readiness.
- Keep version-matched operator help inside the packaged application at `/help`. Organize it by actions—respond to an alert, restore RF data, check recording, understand signal learning, and run an isolated test—and keep normal recovery free of Linux commands.
- All modal surfaces use one accessible dialog boundary with initial focus, contained keyboard focus, inert background content, Escape/backdrop policy, nested-dialog ordering, and focus return. Preserve the existing visual anatomy while applying this behavior.
- The current deployment is an internal Mediterranean maritime pre-work and during-work RF-awareness tool for a known interference environment. Optimize it for truthful early warning, operator triage, and evidence review rather than general-purpose monitoring or predictive claims.
- For this one-receiver deployment, Continuous Watch on one selected physical capture window is the dependable default. Multi-band remains a gap-labelled best-effort survey until live timing proves reserve; Continuous Watch health/readiness must never imply that Multi-band, Radio Survey, or formal Production qualification passed.
- Treat learned field conditions at the known-interference site as a local reference, not a clean baseline. If a representative period cannot be corroborated with independent GNSS/operational information, keep it Checking/Provisional rather than force approval.
- Show the confirmed active RSPdx antenna input and bind it to the RF fingerprint, but do not add automatic port hopping or bias-T control. A/B may be alternative mission inputs only; they are not simultaneous antennas for spoofing detection, and Ant C is outside the current monitored bands.
- Keep evidence replay minimal: same-host Complete or gap-labelled Incomplete sessions, existing spectrum/waterfall, read-only event navigation, and no detector rerun or Field-data mutation. Do not add uploaded archive replay in v1.
- Do not expand this deployment into second-receiver/antenna processing, direction finding, source geolocation, GNSS PVT/message decoding, spoofing classification, calibrated power, IQ capture, ML prediction, cloud/multi-site features, or simultaneous GNSS/radio monitoring.
- Signal-learning progress is active-target and coverage based: isolated rejected visits reduce coverage with bounded reason codes but do not poison a complete UTC hour. Only explicit source/clock-integrity conditions may disqualify a whole hour; legacy ineligible buckets remain fail-closed. Candidate and active-event freezes are target-scoped, while genuine receiver/evidence/resource failures may freeze receiver-wide. Inactive saved baselines never determine normal-user progress.
- Keep qualification and approval copy terse and state-driven. Normal screens must not show generic qualification checklists, development-gate prose, or raw blocker dumps; show only the current state, the specific blocking condition, and the next operator action. Never label signal learning Ready to approve unless the server says approval is currently eligible.
- Treat host memory pressure as a recovery inhibit, not an application fault. Under pressure, pause exports and spectrum delivery, retain status-only updates at 0.2 Hz, freeze field learning, and wait for two minutes of normal host memory before resuming. Coordinate application and SDR recovery with one lock, stagger their checks, and give every new SDRconnect process a 90-second grace period with stale counters reset by process epoch.
- Keep target signal-learning review separate from Production qualification. A reviewable field reference with a current exact fingerprint may be explicitly protected when current RF, evidence, and resource health are safe; sticky historical commissioning faults remain fail-closed for Production qualification but do not force completed learning to restart. Label reviewable references as Review signal learning, never as continued collection.
- Fugro is a selectable frequency window inside Continuous Watch and Multi-band Survey, not a separate operator task. Operators multi-select expected regional satellites after choosing that window; all selected carriers share the one 1545.7425 MHz physical capture and one aligned spectrum/waterfall. Beam selection changes guides and evidence metadata, not tuner load or baseline identity; RF Monitor observes relative RF activity and does not decode corrections or claim service integrity.
- Normal Monitoring customization is catalog-based: operators choose supported physical frequency windows and Fugro satellites. Arbitrary numeric single-frequency focus remains an Engineer tool so unsupported tuning cannot masquerade as an operational watch configuration.
- In view-only Settings, monitoring task cards remain browsable so operators can inspect Continuous Watch, Multi-band Survey, and Radio Survey before unlocking. Previewing a task must not mutate the draft or saved settings; all task-specific write controls remain disabled until the protected session is unlocked.
- Treat deployment as an on-machine release to the local RF Monitor service at `http://127.0.0.1:8080/`. Do not publish or update a Sites-hosted version unless the user explicitly requests a remote Sites deployment.
- Alert sensitivity (`settings.alerting`) is separate from the signal-learning rules (`settings.detection`). Only the learning rules are hashed into baseline fingerprints, and they alone decide what is learned; never move alert thresholds back into them. Sensitivity offers Conservative, Standard (default), Sensitive and Very sensitive presets, plus Custom values in Advanced › Alert rules and per-window overrides. Preset values live on the server and reach the browser through `SettingsRevision`. A sensitivity change applies live: no retune, no learning restart, and open incidents stay open with a timeline entry.
- The alert classifier is segment based: band-wide share, wider-than-narrow partial-band blocks, per-segment narrow peaks, a noise-floor rise, and optional single-frame bursts. Raised checks of any shape count together, and the vote gap follows the window's revisit objective. Keep the public `kind` values for compatibility, put the specific rule in `detailKind`, and keep GNSS verdicts at "Suspected RF interference" (one helper: `rfVerdictFor`).
- Settings saves are classified before Apply and the footer states the impact. Alert sensitivity, site, time zone, retention and report identity apply live. Monitoring and scan edits retune the receiver. Learning-rule edits restart learning and need server-enforced confirmation (428 without it).
- Every incident must explain itself. It keeps an immutable `trigger` (rule, measured against threshold, persistence, disturbed MHz ranges, policy and reference), running `peak` values, a bounded coded `timeline`, and a hex trigger snapshot in the evidence session. Show disturbed frequencies, not only the checked window.
- Incident drawer order: verdict, status and evidence chips; Summary (disturbed frequencies, start, duration); Action; Why this alert (one plain sentence plus measured-versus-alert-level bars in "× normal variation", MHz and checks); the trigger snapshot picture; Timeline; Notes; Evidence (package, Incident report, package SHA-256); Technical details collapsed. Multiples of normal variation are operator-facing for transparency; raw z-values, hashes and IDs stay in Technical details.
- The client incident report is built once as `report.json` and rendered as A4 HTML (also shown in the app in a sandboxed frame) and as a PDF made with pdf-lib, using the same charts as vector graphics. It has a cover (company logo and name, client, vessel, project, site), a summary, why the alert was raised, the recorded spectrum and waterfall, a timeline, analysis, receiver and configuration, notes, evidence integrity, and limitations and terms. Use plain wording and UTC with local time.
- Incident evidence packages are named `RF-Incident_<start>_<window>_<id8>.zip` and contain the report (PDF, HTML, JSON), `README-VERIFY.txt`, the trigger snapshot, screenshots, note files, windowed logs, source-session integrity records and `export-record.json`, all covered by `manifest.json` (`packageType: incident-evidence`) and `SHA256SUMS.txt`.
- Typography must stay consistent with the Quiet Mission Board. New UI uses only the existing type scale (8px uppercase micro labels, 9px captions, 10px secondary, 11px body and rows, 13px card and panel titles, 15px drawer headline) through the `--type-*` tokens. It reuses existing components: `mission-panel`/`mission-panel-heading`, `mission-choice-grid`, `read-only-grid`, `schedule-capacity`, `incident-heading`/`incident-section` rows, and engineer panels. Do not add new font sizes, global font-size overrides, or uppercase letter-spaced section headings. Reports and charts use the dashboard font stack.
